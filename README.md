# Monitoring

Tampermonkey-скрипты для работы с платёжными тикетами в TH Management. Репозиторий устроен так, что скрипты **автообновляются** у всех, кто их установил — правишь код здесь, поднимаешь версию, пушишь в `main`, и у всех подтягивается новая версия сама.

## Установка

Первые два скрипта нужно установить **оба** — они работают в паре (подробнее в разделе [«Как устроена система»](#как-устроена-система)). Третий и четвёртый независимы и ставятся по желанию.

Открыть ссылку в браузере с установленным [Tampermonkey](https://www.tampermonkey.net/) и подтвердить установку:

1. [TH Management — Bulk Approve Tickets (225)](https://raw.githubusercontent.com/partenkoEgor/Monitoring/main/scripts/th-bulk-approve.user.js) — массовая обработка тикетов (два режима: «225» и «239»)
2. [Auto-close SweetAlert2 success popups](https://raw.githubusercontent.com/partenkoEgor/Monitoring/main/scripts/th-autoclose-swal.user.js) — автозакрытие штатных попапов
3. [TH Management — Team Helper](https://raw.githubusercontent.com/partenkoEgor/Monitoring/main/scripts/th-team-helper.user.js) — превью вложений, предыдущий статус закрытых тикетов, поиск лимитов в Confluence, справочник админов в истории тикета, автоподстановка Reddy ID и дат в фильтре, копирование данных тикета в буфер обмена, компактные кнопки вместо длинных ссылок на файлы
4. [TH Management — Dark Theme Recolor](https://raw.githubusercontent.com/partenkoEgor/Monitoring/main/scripts/th-dark-theme.user.js) — перекраска встроенной тёмной темы сайта в более тёмную и контрастную

После установки проверить в панели Tampermonkey, что скрипты **включены** (переключатель в списке).

Отдельно стоит **обкаточная версия Bulk Approve** — она ставится только тем, кто участвует в проверке нового режима, см. раздел [«Обкаточная версия (BETA)»](#обкаточная-версия-beta).

## Как устроена система

Скрипты специально разделены на независимые файлы:

| Скрипт | Назначение | Где действует |
|---|---|---|
| **Bulk Approve Tickets (225 / 239)** | Массовая обработка тикетов, две кнопки на экране (225 и 239) | Только страницы `paymentsupport*` (3 домена) |
| **Auto-Close SweetAlert2** | Автоматически закрывает штатные попапы с «OK!» | Весь `backoffice/*` (3 домена) |
| **Team Helper** | Восемь независимых помощников при ручном разборе тикетов | `paymentsupport*`, `ExtendedPaymentRequestList*` (3 домена) |
| **Dark Theme Recolor** | Перекрашивает встроенную тёмную тему в более тёмную и контрастную | Весь сайт (3 домена) |

Team Helper стоит особняком: он ничего не нажимает и не отправляет за оператора, а только показывает информацию (превью вложений, предыдущий статус, лимиты из Confluence, справочник админов), заполняет поля — диапазон дат в фильтре и Reddy ID в модалке экспорта — по кнопке копирует собранные данные тикета в буфер обмена — тоже без автоматической отправки — и приводит длинные ссылки на файлы к компактным кнопкам, не меняя сами адреса. Поэтому он безопасно сочетается с массовыми прогонами и не мешает им.

У Auto-Close более широкий охват — он нужен во всей админке, а не только во время массовых прогонов. При этом Bulk Approve имеет свой собственный резервный обработчик тех же попапов на случай, если Auto-Close почему-то не сработает вовремя. Это дублирование безвредно и сделано намеренно.

**Объединять их в один скрипт не стоит**: либо пришлось бы расширять `@match` кнопок Bulk Approve на весь бэкофис (кнопки вылезали бы везде), либо сужать Auto-Close только до paymentsupport (терялось бы автозакрытие попапов на остальных страницах).

Dark Theme Recolor по той же причине не встроен в Team Helper: перекраска темы нужна на всём сайте, а у Team Helper `@match` ограничен двумя страницами тикетов (`paymentsupport*`, `ExtendedPaymentRequestList*`) — `@match` общий на весь файл, расширять его на весь сайт ради одной функции не стали, чтобы остальные десять не начали монтироваться везде.

## Bulk Approve Tickets (225 / 239)

`scripts/th-bulk-approve.user.js` — текущая версия: **2.10**.

### Что делает

Проходит по всем тикетам, видимым в таблице на текущей странице списка платёжных запросов, и для каждого:

1. Проверяет колонку **External Status** — если её значения нет в списке статусов выбранного режима, тикет пропускается.
2. Для режима **239** проверяет колонку **Transaction Status** — работает только с тикетами, где транзакция в статусе **rejected**; остальные пропускаются, даже если External Status подходит (см. ниже).
3. Для режима **239** дополнительно проверяет колонку **Amount** — если сумма равна `0`, скрипт берёт сумму из колонки **Transaction Amount** и вписывает её в поле **Amount by receipt** внутри окна Edit (см. ниже).
4. Для подходящих тикетов открывает Edit, ставит целевой статус в выпадающем списке Status и жмёт **Apply**.
5. Ждёт, пока модалка закроется (значит, сохранение прошло).
6. Ловит и логирует любые всплывающие окна (кроме штатного «OK!»), которые появляются в процессе — например, предупреждение о дублирующейся транзакции.
7. В конце показывает итоговую сводку и список тикетов, которые нужно проверить вручную.

На экране — две независимые кнопки запуска (режима), одна общая кнопка **СТОП** (одновременно может выполняться только один прогон):

| Кнопка | External Status тикета (фильтр) | Целевой статус | Доп. проверки |
|---|---|---|---|
| **Bulk Approve (225)** | `Approved (M)` | `225 Approved by agent` | — |
| **Bulk Response (239)** | `The money has not been sent, cancel it (M)`, `Adjust the payout amount (M)`, `185 Limit reached on the recipient side (M)`, `191 Recipient's details are not correct (M)`, `199 Request statement for payout (M)`, `203 Sent (M)`, `238 Revision needed (M)` | `239 Response to user (M)` | Обязательно `Transaction Status = rejected`; при `Amount = 0` подставляет сумму из `Transaction Amount` |

Вся остальная механика (поиск полей, отлов попапов, отчёт, кнопка СТОП, поиск колонок по названию) — общая для обоих режимов.

### Статус транзакции (только режим 239, с версии 2.9)

Режим 239 закрывает статусом `239 Response to user (M)` любой вывод, по которому **транзакция отклонена**. Причина отказа у каждого своя — отсюда и широкий список подходящих External Status в таблице выше.

Один External Status такой тикет не опознаёт: например `203 Sent (M)` стоит и у нормальных отправок, где закрывать тикет ответом пользователю нельзя. Поэтому решающая проверка — колонка **Transaction Status**:

- значение сверяется по словам, а не строкой целиком — подходят `Rejected`, `rejected`, `3 Rejected`, `Rejected (M)`;
- любой другой статус (`Approved`, `Pending`) или **пустая ячейка** — тикет пропускается и даже не открывается, в отчёте появляется строка «Пропущено (транзакция не rejected)» со сводкой по значениям колонки;
- если колонки **Transaction Status** на экране нет — **прогон не начинается**: сверять условие нечем, а обрабатывать «на авось» тут слишком дорого. Скрипт скажет, что колонку нужно включить в настройках таблицы.

Режим 225 колонку `Transaction Status` не проверяет — у него условие только по External Status.

Значения External Status сравниваются без учёта регистра, лишних пробелов и **числового кода в начале**: в фильтре статус подписан как `203 Sent (M)`, а в колонке таблицы тот же статус может выводиться без кода — сравнение «как есть» тогда молча не находило бы ни одного тикета.

### Подстановка суммы при Amount = 0 (только режим 239)

У части тикетов 239 в колонке **Amount** стоит `0`. Раньше скрипт такие тикеты просто пропускал, и оператор доделывал их руками: копировал сумму из колонки **Transaction Amount** в поле **Amount by receipt** и менял статус. С версии 2.6 скрипт делает это сам.

Как это работает:

1. Обе колонки — **Amount** и **Transaction Amount** — ищутся по названию в шапке таблицы. Резервных номеров у них нет намеренно: прочитать не ту денежную ячейку хуже, чем не прочитать ничего. Если колонка не нашлась, скрипт один раз предупредит в консоли, а тикеты с нулевой суммой просто пропустит, как раньше.
2. Название **Transaction Amount** сначала ищется точно, а если не нашлось — по подстроке среди заголовков, содержащих оба слова (`transaction` и `amount`). Это покрывает варианты вроде `Transaction amount, USD` и не путается с обычной колонкой **Amount**.
3. Значение вписывается **чистым числом**: из ячейки убираются валюта и пробелы всех видов, разделители тысяч отбрасываются, десятичный разделитель приводится к точке (`1 500.00 USD` → `1500.00`). Разделители разбираются по правилам: если есть и точка, и запятая — десятичным считается последний из них; если только запятая — она десятичная при 1-2 цифрах после неё и разделитель тысяч в остальных случаях. Формат живёт в одной функции `formatAmountForReceipt`.
4. Перед вставкой скрипт сверяет, что нормализованная строка — **то же самое число**, что в ячейке. Не сошлось (или ячейку вообще не удалось разобрать) — тикет помечается `amount-format-unclear` и **не трогается**: лучше оставить его человеку, чем записать не ту сумму.
5. Сумма вписывается **до** выбора статуса и до Apply, и только после того, как скрипт убедился, что открыт нужный тикет. Если подстановка сорвалась — статус остаётся нетронутым, и тикет не оказывается обработан наполовину.
6. После записи скрипт рассылает `blur` (маски часто нормализуют значение именно по нему) и **читает поле обратно**. Если оно опустело или там другое число, тикет помечается `amount-not-accepted`, окно закрывается через Cancel, статус не меняется. Сравнение **численное**: `1 500.00` и `1500.00` — одно и то же, а не расхождение.
7. После Apply скрипт **проверяет, что сумма действительно сохранилась** — см. следующий раздел.

Когда тикет всё-таки пропускается:

- **Брать нечего** — `Transaction Amount` пуст, равен нулю или там не число. Тикет помечается `skipped`/`zero-amount` и **не открывается вообще** (поведение до 2.6).
- **Поле уже заполнено** — в окне Edit в `Amount by receipt` уже стоит какое-то значение, хотя в списке `Amount = 0`. Скрипт **ничего не перезаписывает** и не меняет статус: это расхождение должен посмотреть человек. Тикет помечается `skipped`/`amount-already-filled`, а в отчёт попадают оба значения — что стоит в окне и что стоит в списке.

Все тикеты, где скрипт **изменил денежное поле**, выводятся в итоговом окне отдельным списком «Вписана сумма из Transaction Amount» с указанием суммы. Тот же список доступен в консоли: `window.__bulkApproveAmountFilled`.

### Проверка, что сумма сохранилась (с версии 2.7)

В 2.6 доказательством считалось чтение значения из поля сразу после записи. Это оказалось **тавтологией**: читалось то же самое `input.value`, которое скрипт сам и записал. На Apply уходит внутренняя модель Vue, и если она значение не подхватила (или бэкенд не разобрал строку с валютой), тикет закрывался с новым статусом, но **без суммы**. Окно «Amount on receipt field must be filled in» при этом не появлялось: оно про **пустое** поле, а здесь поле было непустым — просто негодным.

С 2.7 после Apply скрипт проверяет результат:

1. **Быстрый путь.** Смотрит колонку **Amount** в строке: после сохранения там должна появиться сумма. Совпало — готово, ни одного лишнего окна.
2. **Путь сомнения.** В колонке всё ещё ноль (или таблица не перечиталась с сервера) — скрипт **переоткрывает Edit**, сверяет номер тикета в заголовке, читает поле `Amount by receipt` и закрывает окно через Cancel. Окно закрывается при любом исходе: незакрытое уронило бы следующий тикет каскадом.

Все сравнения численные. Вердикт попадает в результат тикета (`amountVerified`):

| Вердикт | Что значит | Где в отчёте |
|---|---|---|
| `saved` | сумма на месте | обычный список «Вписана сумма из Transaction Amount» |
| `not-saved` | статус изменён, а суммы нет | громкий блок «⚠ СУММА НЕ СОХРАНИЛАСЬ», плюс `window.__bulkApproveAmountNotSaved` |
| `unverified` | проверить не удалось (строка пропала, окно не открылось, номер не сошёлся) | блок «Сумма вписана, но проверить не удалось» |

**Тикеты из блока «СУММА НЕ СОХРАНИЛАСЬ» чинятся повторным прогоном:** Amount в списке остался `0`, External Status не менялся — скрипт возьмётся за них снова и допишет сумму.

Если сумма не сохранилась у **трёх тикетов подряд**, прогон останавливается сам: значит, сайт перестал принимать сумму в том виде, в каком её вписывает скрипт, и гнать дальше, трогая деньги впустую, вредно. Проверку целиком можно выключить флагом `CONFIG.verifyAmountSaved` — но тогда возвращается ровно та проблема, ради которой она появилась.

### Свежие и зависшие тикеты (с версии 2.10)

В сводке отчёта обработанные тикеты разбиваются по времени ожидания — чтобы было видно, разгребали ли текущий поток или накопившийся хвост:

```
Успешно: 100
  • из них свежих (меньше 24 ч): 45
  • из них зависших (24 ч и больше): 55
```

- возраст берётся из колонки **Processing Date** и фиксируется **в момент обработки тикета**, а не в конце прогона — это то, сколько тикет реально прождал;
- порог задаётся в `CONFIG.staleAfterHours` (по умолчанию `24`). Ровно 24 часа считаются зависшими: граница включающая;
- считаются только **успешно обработанные** тикеты. Пропущенные в статистику не идут, даже если провисели дольше всех — прогон их не трогал;
- сравнение идёт **по часам браузера**. Если сайт однажды начнёт показывать эту колонку в другом часовом поясе, граница уедет на величину смещения: у тикетов возле самой границы отнесение может измениться, общая картина — нет.

Дата и время в ячейке стоят на разных строках, и в тексте между ними может не оказаться вообще никакого разделителя (`2026-09-2214:45:59`), поэтому дата разбирается регулярным выражением по цифрам, а не делением по пробелу. Несуществующие даты (`2026-02-31`) отбрасываются — иначе `Date` молча перенёс бы такую на март.

Если колонки на экране нет или дату прочитать не удалось, статистика не выдумывается, а честно об этом говорит:

```
  • возраст не считали: на экране нет колонки Processing Date
  • из них с нечитаемой Processing Date: 2
```

Вторая строка — сигнал, что на сайте поменялся формат колонки: без неё смена формата тихо записала бы все тикеты в «свежие». Поимённый список зависших лежит в консоли: `window.__bulkApproveStaleTickets`.

### Итоговое окно и копирование в таблицу (с версии 2.8)

Раньше отчёт показывался через `alert()`: текст в нём нельзя выделить, а суммы потом нужно фиксировать в своей таблице учёта. Теперь скрипт рисует своё окно:

- **сверху** — тот же текст отчёта, но его можно выделить и скопировать;
- **снизу** — поле с готовой таблицей и кнопка **«Скопировать»**.

В поле три колонки через табуляцию — **Ticket ID, Transaction ID, Amount** — без строки заголовка, чтобы вставлять прямо в существующую таблицу. Табуляция разбирается Excel и Google Sheets по колонкам сама:

```
19406925	19993860563	1500.00
19406928	19993860571	840.50
19406929	19993860588	990.00
```

Попадают туда **только подтверждённые** тикеты: те, где скрипт вписал сумму и убедился, что она сохранилась. Тикеты из блоков «СУММА НЕ СОХРАНИЛАСЬ» и «проверить не удалось» в таблицу **не попадают** — в учёт должно уходить то, что реально лежит в тикетах, а не то, что скрипт пытался вписать. Их сначала нужно разобрать руками.

Если кнопка «Скопировать» не смогла записать в буфер (браузер не дал доступ), она выделит текст и подскажет нажать Ctrl+C. Если вписанных сумм в прогоне не было, поля для копирования нет вовсе. Тот же список доступен в консоли: `window.__bulkApproveCopyRows`.

Окно закрывается кнопкой **«Закрыть»**, клавишей **Esc** или кликом мимо него. Если по какой-то причине окно не отрисуется, скрипт откатится на обычный `alert` — отчёт в любом случае дойдёт до человека.

### Как запускать

1. Открыть страницу со списком тикетов, настроить нужные фильтры (даты, статус и т.д.) как обычно.
2. Нажать нужную кнопку в правом нижнем углу — **«Bulk Approve (225)»** или **«Bulk Response (239)»**, в зависимости от того, какие тикеты нужно обработать.
3. Подтвердить диалог с числом найденных на экране тикетов.
4. Скрипт последовательно обработает все строки. В любой момент можно нажать красную кнопку **«СТОП»**, которая появляется рядом с кнопками запуска на время прогона — скрипт корректно завершит текущий шаг (не обрывает на середине клика) и покажет промежуточный отчёт.
5. По завершении (или после СТОП) появится итоговое всплывающее окно со сводкой.

> **Важно:** обрабатываются только тикеты, физически загруженные на странице сейчас. Если тикетов больше, чем помещается на одной странице/фильтре — пагинация не обходится автоматически, нужно прогонять скрипт для каждой порции отдельно.

- **Успешно** — тикет обработан, модалка закрылась после Apply.
- **Пропущено (не тот External Status)** — External Status тикета нет в списке статусов этого режима, тикет не трогали.
- **Пропущено (транзакция не rejected)** — только для режима 239: External Status подошёл, но транзакция не отклонена (или ячейка `Transaction Status` пуста). Тикет даже не открывали. Ниже идёт сводка по значениям колонки — по ней видно, читается ли `Transaction Status` вообще.

- **⚠ статус изменён, но сумма НЕ сохранилась** — проверка после Apply показала, что суммы в тикете нет. Самая важная строка отчёта: тикет выглядит обработанным, но денег в нём нет.
- **Пропущено (Amount by receipt уже заполнен)** — только для режима 239: в окне Edit сумма уже стояла, хотя в списке `Amount = 0`. Ничего не меняли, статус не трогали.
- **Пропущено (непонятный формат суммы)** — в `Transaction Amount` что-то есть, но это не разбирается как сумма. Тикет не трогали, чтобы не записать не то число.
- **Ошибок** — что-то пошло не так на одном из шагов. Под этой строкой идёт разбивка по причинам, чтобы сразу отличить «сайт лёг целиком» от «несколько разных мелочей».
- **Требуют ручной проверки на дубликаты** — тикеты, где всплыло нестандартное окно во время обработки (формат `Ticket ID - Transaction ID`). Их нужно открыть руками — вероятно, транзакция уже используется в другом обращении.
- **⚠ СУММА НЕ СОХРАНИЛАСЬ** — статус уже изменён, а сумма не записалась. Нужно поправить вручную или прогнать скрипт ещё раз.
- **Вписана сумма из Transaction Amount** — тикеты, где скрипт изменил денежное поле и **проверил**, что сумма на месте. Они же попадают в поле для копирования (см. ниже).
- **Сумма вписана, но проверить не удалось** — статус изменён, сумму стоит глянуть глазами.
- **Пропущены: Amount = 0, а в Transaction Amount нечего взять** — список Ticket ID для ручной проверки (только режим 239).
- **Пропущены: Amount by receipt уже заполнено** — расхождение между списком и формой, с обоими значениями. Нужно посмотреть руками (только режим 239).

### Как ловятся попапы

Отдельный наблюдатель следит за всеми окнами SweetAlert2 (`.swal2-popup`):

- Штатное **«OK!»** (зелёная галочка, кнопка «OK», без кнопки отмены) — закрывается молча, без записи в отчёт.
- Любое **другое** окно — записывается в отчёт с привязкой к тикету и его Transaction ID.
  - Без кнопки отмены и **не** с иконкой ошибки — единственная доступная кнопка нажимается автоматически, чтобы не блокировать прогон, но текст всё равно попадает в отчёт.
  - С иконкой **error** (например, «Amount on receipt field must be filled in») — скрипт ничего не нажимает, оставляет окно на экране, чтобы можно было прочитать текст. Тикет в этом случае, скорее всего, попадёт в «Ошибки» (таймаут на закрытие модалки), а незакрытый попап нужно будет закрыть вручную перед тем, как скрипт перейдёт к следующему тикету.
  - С кнопкой отмены (сайт предлагает реальный выбор) — скрипт тоже ничего не нажимает, оставляет окно как есть.

Проверить детали после прогона можно в консоли (F12 → Console):

```js
// Таблица со всеми пойманными окнами (тикет, TXN ID, иконка, заголовок, текст, была ли кнопка отмены)
window.__bulkApproveCapturedPopups

// Полный список результатов по каждому тикету
window.__bulkApproveLastResults

// Найти конкретный тикет в результатах
window.__bulkApproveLastResults.find(r => r.ticketId === '19406922')
```

### Настройки (CONFIG и WORKFLOWS)

В начале файла скрипта есть блок `CONFIG` с общими для всех режимов таймингами:

```js
const CONFIG = {
  stepDelay: 250,              // пауза между шагами внутри одного тикета (мс)
  waitTimeout: 8000,           // сколько ждать появления/исчезновения элемента (мс)
  betweenTicketsDelay: 2000,   // пауза между тикетами (мс)
  tableReloadTimeout: 15000,   // сколько ждать возвращения опустевшей таблицы (мс)
  blockingPopupTimeout: 5000,  // сколько ждать закрытия чужого окна (мс)
  maxConsecutiveFailures: 3,   // столько ошибок подряд — и прогон встаёт сам
  verifyAmountSaved: true,     // проверять после Apply, что сумма сохранилась
  staleAfterHours: 24,         // с какого возраста тикет считается зависшим (часы)
};
```

- Если Vue не успевает среагировать (элементы не находятся, хотя видны на экране) — увеличить `stepDelay` и/или `waitTimeout`.
- `betweenTicketsDelay` влияет только на скорость прогона; пропущенные тикеты эту паузу не ждут.
- `staleAfterHours` влияет только на статистику в отчёте — на то, какие тикеты скрипт обрабатывает, он не влияет никак.
- `maxConsecutiveFailures` можно поднять, если сайт регулярно «моргает» и прогон встаёт слишком рано, но снижать его ниже 2 не стоит — тогда единичный сбой будет валить весь прогон.

Ниже — массив `WORKFLOWS`, по одному объекту на каждую кнопку/режим:

```js
const WORKFLOWS = [

    id: '225',
    buttonLabel: 'Bulk Approve (225)',
    buttonColor: '#2ABFCF',
    requiredExternalStatuses: ['Approved (M)'], // с какими External Status брать тикет
    searchTerm: '225',                        // что печатается в поле поиска статуса
    statusMatch: (text) => { ... },           // как определяется нужная опция статуса
    targetStatusLabel: '225 Approved by agent', // только для текста диалогов/отчёта
  },
  {
    id: '239',
    // ... requiredExternalStatuses / searchTerm / statusMatch / targetStatusLabel — та же схема,
    // в requiredExternalStatuses здесь шесть статусов (см. таблицу режимов выше)
    requiredTransactionStatus: 'rejected', // брать тикет только если транзакция отклонена (см. раздел выше)
```

Чтобы добавить ещё один режим (ещё одну кнопку) — достаточно добавить новый объект в `WORKFLOWS`: скрипт сам создаст для него кнопку на экране и подключит общую логику (поиск полей, отлов попапов, отчёт, кнопка СТОП, поиск колонок по названию).

### Диагностика ошибок по тикету

Каждая запись в `window.__bulkApproveLastResults` содержит `status` и, если это ошибка — `reason`. В итоговом окне вместо кода показывается формулировка из колонки «Текст в окне» (словарь `REASON_LABELS` в скрипте):

| `reason` | Текст в окне | Что произошло | Что проверить |
|---|---|---|---|
| `no-edit-link` | в строке нет кнопки Edit | Не найдена кнопка/ссылка Edit в строке | Не поменялась ли колонка Actions или её содержимое |
| `modal-not-shown` | окно Edit не открылось | После клика Edit модалка не появилась за `waitTimeout` | Не изменилась ли верстка модалки; сайт может тормозить |
| `no-amount-receipt-field` | в окне нет поля Amount by receipt — сумму вписать некуда | Скрипт собирался подставить сумму, но поля `Amount by receipt` в форме нет (или в нём нет текстового `input`) | Не переименовали ли поле на сайте; проверить `findFieldGroup(modal, 'Amount by receipt')` |
| `amount-not-accepted` | сайт не принял вписанную сумму (поле сбросилось) — ничего не меняли, проверь вручную | Сумму вписали, но после `blur` в поле оказалось пусто или другое число. Статус не меняли, Apply не жали | Скорее всего, у поля маска, которой не подходит формат — посмотреть, что именно остаётся в поле, и поправить `formatAmountForReceipt` |
| `no-status-field` | в окне не появилось поле Status (сайт не отрисовал форму) | Поле Status не появилось в модалке за `waitTimeout` (форма не отрендерилась) | Сайт сильно тормозит — увеличить `waitTimeout`; либо изменился текст лейбла или структура `.form-add .input-group` |
| `stale-modal-before-edit` | не закрылось окно от предыдущего тикета | Перед кликом Edit на экране висела незакрытая модалка от предыдущего тикета, и закрыть её не удалось — **прогон остановлен автоматически** | Закрыть модалку вручную, проверить последние failed-тикеты и запустить прогон заново |
| `modal-ticket-mismatch` | открылся ДРУГОЙ тикет — ничего не меняли | Открылась модалка **другого** тикета, чем ожидалось — ничего не изменено, **прогон остановлен автоматически** | Обновить страницу и запустить заново. Если повторяется — прислать лог: значит, таблица перерисовывается слишком агрессивно |
| `modal-title-unreadable` | не удалось прочитать номер тикета в заголовке окна — ничего не меняли | Не удалось прочитать номер тикета в заголовке модалки, проверка невозможна — **прогон остановлен автоматически** | Скорее всего изменилась вёрстка модалки, нужно поправить `getModalTicketId(...)` в скрипте |
| `blocking-popup` | на экране висело незакрытое окно сайта | На экране висит незакрытое окно сайта (обычно сообщение об ошибке) — **прогон остановлен автоматически** | Прочитать и закрыть окно, затем запустить прогон заново |
| `row-disappeared` | строка исчезла из таблицы — тикет даже не открывали | Строка тикета пропала из таблицы, тикет **не обработан** | Тикет попадёт в список «ТИКЕТЫ С ОШИБКАМИ» — прогнать заново или проверить вручную |
| `no-multiselect-tags` | поле Status непривычной вёрстки — скрипт его не понял | Не найден `.multiselect__tags` внутри поля Status | vue-multiselect мог измениться/обновиться |
| `dropdown-not-opened-or-no-match` | не открылся список статусов или нужного статуса в нём нет | Список не раскрылся, или в нём нет опции целевого статуса этого режима | Проверить `statusMatch` соответствующего объекта в `WORKFLOWS`; в консоли рядом выводится HTML поля Status для отладки |
| `no-apply-button` | не найдена кнопка Apply | Не найдена кнопка Apply в модалке | Изменилась верстка блока кнопок `.filter.btn-block` |
| `modal-not-closed` | нажали Apply, но окно не закрылось — ПРОВЕРЬ ВРУЧНУЮ, сохранился ли статус | После клика Apply модалка не закрылась за `waitTimeout` | Скорее всего, всплыло окно с ошибкой/предупреждением — проверить `window.__bulkApproveCapturedPopups` для этого тикета |
| `exception` | непредвиденная ошибка скрипта (подробности в консоли) | Необработанное исключение во время обработки тикета | Смотреть полный текст ошибки в консоли (`console.error`) |

Если код ошибки почему-то не найден в словаре, в окно попадёт `неизвестная причина: <код>` — это значит, что в скрипт добавили новый `reason`, но забыли добавить формулировку в `REASON_LABELS`.

Любая ошибка не прерывает весь прогон целиком — скрипт помечает тикет как `failed` и переходит к следующему.

Записи со `status: 'skipped'` тоже содержат `reason`:

- `wrong-external-status` — External Status тикета нет в списке статусов режима;
- `transaction-not-rejected` — только режим 239: транзакция не в статусе `rejected` (или ячейка пуста). В записи лежит `transactionStatus` — сырой текст ячейки. Тикет не открывали;
- `no-transaction-status-column` — только режим 239: колонку `Transaction Status` не удалось прочитать уже во время прогона (набор колонок менялся). Тикет не открывали; в отчёте появляется предупреждение с советом перезапустить прогон;
- `zero-amount` — только режим 239: `Amount = 0`, и в `Transaction Amount` нечего взять;
- `amount-format-unclear` — только режим 239: в `Transaction Amount` что-то есть, но это не разбирается как сумма (`12.34.56`, `USD`, `—`). В записи лежит `transactionAmountRaw` — сырой текст ячейки. Тикет не трогали;
- `amount-already-filled` — только режим 239: `Amount = 0`, но поле `Amount by receipt` уже заполнено. В записи лежат оба значения: `existingAmount` (что стоит в окне) и `transactionAmount` (что стоит в списке).

У успешных записей, где скрипт подставил сумму, есть поля `amountFilled` (ровно та строка, которая ушла в форму), `amountVerified` (`saved` / `not-saved` / `unverified`), `storedAmount` (что оказалось в тикете при проверке) и `verifyNote` (как именно проверяли или почему не смогли).

### Защита от записи в чужой тикет

Самый опасный сбой — когда статус и Apply применяются не к тому тикету, который скрипт собирался обработать (именно так в тикет дважды попадала чужая транзакция). Защита выстроена в несколько рубежей:

1. **Сверка номера тикета в модалке (главный рубеж).** После открытия Edit скрипт читает заголовок модалки — он выглядит как `Change ticket no.19983972` — и сверяет номер с тикетом, который собирался править. Если номера не совпали, **скрипт не трогает ничего** и останавливает весь прогон (`modal-ticket-mismatch`). Это ловит проблему по факту, независимо от того, какая именно гонка её вызвала: перерисовалась ли таблица между чтением строки и кликом Edit, или сайт показал старую модалку. Если заголовок вообще не читается (изменилась вёрстка) — прогон тоже останавливается (`modal-title-unreadable`), потому что без этой проверки работать небезопасно.
2. **Работа по номерам тикетов, а не по позициям строк.** Таблица перерисовывается прямо во время прогона; при работе по индексу сдвиг строк молча подсовывал бы не тот тикет либо навсегда пропускал один из них. Теперь каждая строка ищется по своему Ticket ID.
3. **Закрытие модалки при любой ошибке.** При ошибке после открытия модалки скрипт жмёт Cancel и ждёт (до 3 секунд) её фактического закрытия.
4. **Проверка перед каждым кликом Edit.** Если на экране осталась модалка от предыдущего тикета — скрипт пробует закрыть её ещё раз, и если не выходит, останавливает прогон (`stale-modal-before-edit`).
5. **Проверка на чужие окна.** Окна с ошибкой скрипт намеренно не закрывает, чтобы оператор прочитал текст. Но работать «сквозь» них нельзя: у SweetAlert2 модальная подложка, живой человек кликнуть бы не смог. Если такое окно висит дольше 5 секунд, прогон останавливается (`blocking-popup`) с просьбой закрыть окно.

Во всех случаях автоостановки в итоговом окне вместо «Остановлено пользователем» показывается «ПРОГОН ОСТАНОВЛЕН АВТОМАТИЧЕСКИ» и причина.

### Что происходит, когда сайт тормозит или лежит

- **Таблица опустела** (перезагрузка страницы, ошибки сервера) — скрипт ждёт её возвращения до 15 секунд. Раньше он в этот момент молча пролистывал весь остаток списка и рапортовал «Готово», хотя не посмотрел почти ни одного тикета.
- **Три ошибки подряд** — прогон останавливается сам (`maxConsecutiveFailures` в `CONFIG`). Нет смысла гнать сотню тикетов, когда сайт отвечает ошибками, да и сервер лишний раз нагружать не стоит.
- **Отчёт больше не врёт.** Если хоть один тикет из списка остался необработанным — потому что упал на одном из шагов или прогон до него не дошёл — вместо «Готово» показывается «Прогон завершён, но НЕ ВСЕ тикеты обработаны», а сами номера перечисляются с причиной в блоках «⚠ ТИКЕТЫ С ОШИБКАМИ» и «⚠ ПРОГОН НЕ ДОШЁЛ ДО ТИКЕТОВ». Полные списки всегда доступны в консоли: `window.__bulkApproveFailed` и `window.__bulkApproveUnprocessed`.

### Поиск колонок по названию

Скрипт не привязан жёстко к номерам колонок таблицы (`nth-child`). Перед каждым прогоном он:

1. Читает `<th>` в шапке таблицы (`.table-wrapper thead th`).
2. Строит карту «название колонки → её текущий порядковый номер».
3. Использует эту карту для поиска **Ticket ID**, **External status**, **Transaction ID** и **Actions** независимо от порядка колонок у конкретного пользователя.

Если название колонки не находится (шапка не прогрузилась, колонку скрыли/переименовали) — скрипт откатывается на резервный номер (сейчас: External status = 8, Ticket ID = 9, Transaction ID = 11, Actions = 3) и пишет предупреждение в консоль:

```
[BulkApprove] Не найдены колонки по названию: transaction id — для них будут использованы резервные номера.
```

Если видишь такое предупреждение — стоит проверить, не съехали ли резервные номера у конкретного пользователя (можно поправить их прямо в коде функции `getColumnIndex(...)`).

### Ограничения и важные предположения

- Таблица тикетов и модалка Edit рендерятся в основном DOM (не в iframe).
- Поле Status — компонент **vue-multiselect**; открытие списка завязано на фокус внутреннего `<input>`, а не на клик по обёртке.
- Сайт использует **SweetAlert2** для всплывающих окон (не нативные `alert()`/`confirm()`), кроме диалога подтверждения самого скрипта — он использует нативный `confirm()`.
- Обрабатываются только тикеты, уже загруженные на странице; пагинация не листается автоматически.
- Одновременно с этим скриптом может работать другой Tampermonkey-скрипт (авто-датапикер фильтров), который иногда делает полную перезагрузку страницы формой (`method="post"`) — это ожидаемо и не является ошибкой.

### Обкаточная версия (BETA)

`scripts/th-bulk-approve-beta.user.js` — **временный** файл, копия основного скрипта с ещё не обкатанными изменениями. Нужен, чтобы команда продолжала работать на стабильной версии, пока новое проверяется на бою.

Ставится отдельной ссылкой: [TH Management — Bulk Approve Tickets (BETA)](https://raw.githubusercontent.com/partenkoEgor/Monitoring/main/scripts/th-bulk-approve-beta.user.js)

**На время обкатки основной скрипт нужно выключить** в панели Tampermonkey. Оба они добавляют кнопки в один и тот же угол экрана, и две похожие пары кнопок на странице бэк-офиса — это способ однажды нажать не ту. Технически они уживаются (id элементов, подписи кнопок и префикс в консоли у беты свои), но полагаться на это не стоит.

Кнопки беты подписаны словом **BETA**, в консоли её сообщения идут с префиксом `[BulkApproveBETA/…]`.

#### Что в ней нового

Третий режим — **«BETA Bulk Approve по списку (225)»**. Он для тикетов, которые нужно закрыть как `225 Approved by agent`, но у которых **не заполнен Transaction ID**: без номера транзакции сайт закрыть их не даёт.

Номера приходят списком из внешней таблицы. По нажатию кнопки скрипт показывает окно, куда вставляется список парами «Ticket ID → Transaction ID» через табуляцию:

```
22708318	23658907281
22707583	23658797989
```

Дальше он берёт со страницы только те тикеты, которые есть в списке **и** в статусе `Approved (M)`, вписывает номер транзакции, дожидается, пока сайт подтянет данные, ставит статус и жмёт Apply. После Apply проверяет, что номер действительно сохранился — так же, как это делается с суммами начиная с версии 2.7.

**Список можно вставлять целиком.** Тикеты, которых нет на текущей странице, — это норма при работе пачками, и отчёт говорит об этом нейтрально, а не как об ошибке. Скрипт помнит список и то, что уже сделано, между прогонами, и в конце выдаёт три поля для копирования:

1. **оставшиеся Ticket ID** — вставляются прямо в поиск сайта, чтобы набрать следующую пачку;
2. **тикеты с проблемами** — прогнать заново или посмотреть глазами, с причиной у каждого;
3. **таблица «Ticket ID / Transaction ID»** для учёта.

#### Автопилот

Автопилот работает в двух режимах: «по списку (225)» (список пар) и в обычном **«BETA Bulk Approve (225)»** (список одних Ticket ID, см. ниже). В окне ввода списка есть галочка **«Автопилот»** — включена по умолчанию. С ней скрипт сам делает то, что раньше оператор делал руками между прогонами: берёт из списка сотню тикетов, вставляет их в поле фильтра **Ticket ID**, жмёт **Apply**, обрабатывает полученную выдачу, берёт следующую сотню — и так до конца списка.

Сотня — не круглое число «для красоты»: ровно столько умещается на одну страницу выдачи. Больше — и сайт включает пагинацию, а ею скрипт не пользуется принципиально: страницы нестабильны, и прогон по ним терял бы тикеты молча.

Что происходит перед каждой пачкой:

- если блок **Quick filters** свёрнут, скрипт раскрывает его сам;
- номера вписываются в поле и **читаются обратно** — если сайт обрезал вставленное, пачка не запускается;
- после Apply скрипт ждёт, пока таблица перестроится (состав строк перестал меняться, незакрытых запросов нет);
- и главное — **сверяет выдачу с пачкой**. Если на экране оказался хоть один тикет, о котором не спрашивали, значит фильтр не применился, и прогон останавливается. Обрабатывать чужую выборку скрипт не станет.

Прогон останавливается сам ещё в двух случаях: если подставить пачку не удалось (нет поля фильтра, нет кнопки Apply, таблица не перестроилась) и если **три пачки подряд** сайт вернул пустыми — триста тикетов, которых не нашлось, это сломанный фильтр, а не совпадение.

Остановка в любом из этих случаев ничего не теряет: закрытые тикеты остаются отмеченными в памяти списка, остальные лежат в блоке для копирования, и следующий прогон продолжит с того же места.

Галочку можно снять — тогда скрипт работает по-старому, только с тем, что оператор вывел на экран сам, и фильтр страницы не трогает. Если поля фильтра или кнопки Apply на странице нет, галочка выключается и блокируется сама, с объяснением.

**После прогона в поле фильтра остаётся последняя пачка** — таблица на экране показывает именно её. Чтобы вернуть обычную выдачу, поле надо очистить и нажать Apply. Отчёт напоминает об этом последней строкой.

#### Список Ticket ID для обычного 225

У кнопки **«BETA Bulk Approve (225)»** теперь тоже есть окно. В него можно вставить список Ticket ID — **по одному номеру в строке, без других колонок** — и прогнать его автопилотом ровно так же, как список пар. Номера транзакций тут не нужны: тикеты в этом режиме уже заполнены, меняется только статус.

Список **необязателен**. Рядом стоит кнопка **«Запустить по экрану»** — это прежнее поведение кнопки: взять то, что оператор уже вывел на страницу сам. Отдельной кнопкой, а не пустым полем, чтобы запустить прогон без списка нельзя было случайно.

Список работает и без автопилота: тогда он отбирает нужные тикеты среди тех, что на экране, а фильтр страницы не трогается.

Проверка формата строгая: строка, в которой оказалось больше одного значения, считается ошибкой, и прогон не начнётся. Это сделано намеренно — лишняя колонка обычно значит, что скопировали не тот кусок выгрузки, и молча взять из неё первое число было бы худшим из исходов. Повторяющиеся номера схлопываются, про их количество окно сообщает.

У двух списков **разная память**: счётчики обработанного для «по списку (225)» и для обычного 225 хранятся под разными ключами и не пересекаются.

#### Окно вместо confirm

Раз у 225 появилось окно, прежний `confirm()` из этого пути убран: окно само пишет, сколько тикетов на экране, какие External Status будут взяты и какой статус выставится, а его кнопки и есть подтверждение. Два диалога подряд ради одного вопроса были бы лишним кликом на каждом ежедневном прогоне.

У **Bulk Response (239)** окна нет, и `confirm()` там остаётся единственной проверкой — как раньше.

#### Дубль транзакции

Вписав номер, сайт проверяет, не занят ли он другим обращением. Занят — показывает окно вида «Обращение с этим номером транзакции уже создано: 22637108». Сайт двуязычный, и то же окно бывает английским: «A query with this transfer number has already been created: 14385934» — обрабатываются одинаково.

**Скрипт с таким тикетом не делает ничего:** статус не меняет, Apply не жмёт, окно Edit закрывает, тикет выносит в отчёт вместе с номером чужого обращения — и **переходит к следующему**. Прогон не останавливается.

Окно закрывается второй кнопкой (**Cancel** / **Close**). Первую нажимать нельзя: она копирует номер чужого обращения в буфер обмена (**Copy** / **Copy ticket number**), а буфер нужен человеку для вставки списков — затирать его посреди прогона скрипт не вправе. Кнопки ищутся по классам SweetAlert2, а не по подписям, поэтому язык интерфейса на это не влияет.

Почему тикет при этом не закрывается. У SweetAlert2 модальная подложка: живой человек сквозь висящее окно кликнуть не может, а `fireClick` рассылает события напрямую и подложку обходит. На боевом прогоне это и произошло — вопрос сайта остался без ответа, а скрипт под ним выставил статус и нажал Apply, и тикет закрылся с чужой транзакцией. Ровно тот класс инцидента, от которого в этом скрипте уже стоят две другие защиты.

Тикеты, разобранные как дубли, не повторяются в общем списке «требуют ручной проверки на дубликаты» — у них есть свой раздел. Фильтр там по тикету, а не по тексту окна: если прогон остановили раньше, чем скрипт успел вынести вердикт, пойманное окно так и остаётся единственным следом, и прятать его нельзя.

В итоговом окне такие тикеты выдаются отдельным блоком для копирования — парой **Ticket ID / Transaction ID** через табуляцию, чтобы вставить в таблицу и пройтись по ним руками. Номер обращения, которое уже держит транзакцию, есть в тексте отчёта выше.

**Любое другое окно сайта останавливает прогон.** Автоматически закрывается только это, известное, и опознаётся оно по списку формулировок, которые реально видели на боевой странице (`DUPLICATE_POPUP_PATTERNS`). Появится ещё одна локаль или новая редакция текста — её нужно будет добавить туда же. Догадкам там не место: цена ложного совпадения в том, что скрипт сам закроет чужой вопрос.

Та же проверка стоит вторым рубежом непосредственно перед Apply: любое окно сайта на экране в этот момент останавливает прогон, каким бы оно ни было.

#### Что он намеренно НЕ делает

- **не перезаписывает** уже заполненный Transaction ID, если он отличается от списка: такой тикет пропускается целиком, статус у него не меняется;
- **не запускается**, если в списке есть неразобранные строки, один тикет с разными транзакциями или одна транзакция у разных тикетов. Последнее — прямое попадание в историю этого проекта, где чужая транзакция дважды уезжала не в тот тикет;
- **не меняет статус**, если сайт не принял номер или не закончил догружать данные;
- **не листает страницы выдачи**: пачка всегда умещается на одну страницу, а по нестабильной пагинации прогон терял бы тикеты незаметно.

#### Ожидание догрузки данных

После вставки номера сайт идёт за данными транзакции и дозаполняет остальные поля окна. Трогать статус до конца этой загрузки нельзя — ответ сервера перетирает выбранное значение.

Поймать момент по изменениям на странице не получается: замеры на боевой странице показали 3,6 секунды полной тишины между вводом и обновлением полей, а само обновление может свестись к паре секунд в поле даты. Поэтому скрипт ведёт **пассивный журнал сетевых запросов** (обёртка над `XMLHttpRequest`/`fetch`, которая только отмечает старт и финиш) и ждёт конкретные адреса:

| Запрос | Когда уходит | Что это |
|---|---|---|
| `checkPaymentSupportRequestByTrxId` | ~500 мс после ввода | занята ли транзакция другим тикетом — **источник попапа о дубле** |
| `getTransactionInfo` | ~3000 мс после ввода | данные транзакции |
| `GetSubAgentInfo` | следом | данные субагента |

Сайт шлёт **две независимые волны** от одного события ввода, и между ними 2,4 секунды тишины. Поэтому ожидание построено на самом запросе `getTransactionInfo`, а не на времени: фиксированный порог сломался бы на тикете, где первая волна отвечает медленно. Пороги и адреса лежат в `CONFIG` (`transactionLoad*`) и правятся без изменения логики.

Если вторая волна не пришла за отведённый срок, прогон идёт дальше, но тикет помечается — молчать об этом нельзя. Если не ушёл вообще ни один запрос, значит сайт не увидел ввод: статус не меняется, тикет уходит в ошибки.

#### Что означают цифры в сводке

Две строки считаются по тому, что прогон **реально запросил у сайта**, а не по всему списку:

- «Всего тикетов из списка показал сайт: N (запрошено в применённых пачках: M, всего в очереди: K)»;
- «Сайт не показал по фильтру» = запрошено минус показано.

Иначе после одной применённой пачки на сотню отчёт заявлял «сайт не показал 710», хотя из этих 710 большая часть была закрыта в прошлые прогоны, а остальные лежали в пачках, до которых прогон не дошёл.

Списки в тексте отчёта обрезаются на сороковой строке, и обрезанный список **обязан об этом сказать** — «… и ещё N». Блоки для копирования не обрезаются никогда: из них работают руками.

#### Счётчик прогресса

Во время прогона над кнопками висит панель: номер текущего тикета, счётчики и **текущее действие** («жду загрузку данных транзакции», «ставлю статус», «жму Apply»). Прогон сотни тикетов идёт больше десяти минут, и по этой строке видно, что скрипт ждёт сайт, а не завис.

В режиме автопилота там же видно **номер пачки** («Пачка 2 из 5») и сквозной счёт по списку («из списка: 137 из 480») — он растёт по ходу прогона, а не показывает число, которое было на старте.

#### Как вернуть изменения в основной скрипт

Бета — временная ветка, а не второй продукт. Когда обкатка закончится:

1. скопировать содержимое беты в `scripts/th-bulk-approve.user.js`;
2. вернуть шапку основного скрипта, подняв версию до **2.12** (бета несёт оба изменения сразу: режим по списку и автопилот);
3. убрать `-beta` из id элементов (`bulk-approve-beta-*`) и из ключей `localStorage` (их два — `LIST_STORAGE_KEYS`);
4. убрать «BETA» из подписей кнопок и из префикса в консоли;
5. удалить `scripts/th-bulk-approve-beta.user.js` и этот раздел README.

Список короткий намеренно: в бете переименовано только то, что обязано отличаться. Имена `window.__bulkApprove*` оставлены прежними именно ради простоты переноса.

## Auto-close SweetAlert2 success popups

`scripts/th-autoclose-swal.user.js` — текущая версия: **1.7**.

### Что делает

Работает на всех страницах `backoffice/*` (не только paymentsupport) и следит за появлением попапов SweetAlert2. Закрывает автоматически **только** те, что строго соответствуют штатному подтверждению сохранения:

- иконка успеха (`swal2-icon-success`);
- содержимое — текст `"OK!"` (с учётом визуально похожих кириллических букв О/о/К/к, которые иногда попадают в текст по ошибке раскладки/копипаста);
- кнопка подтверждения с текстом `"OK"`;
- **нет** кнопки отмены.

Если хотя бы одно условие не выполняется — попап не трогается, чтобы случайно не закрыть окно с реальным предупреждением или ошибкой.

Работает независимо от Bulk Approve и нужен для всей админки: например, при обычном ручном сохранении карточек вне массовых прогонов.

### Диагностика

Каждое автозакрытие пишется в консоль (F12 → Console):

```
[AutoClose] Закрыл попап: title "...", содержимое "OK!", кнопка "OK"
```

С версии 1.7 в лог добавлен `title` — если когда-нибудь окно с реальным сообщением (например, валидационной ошибкой) начнёт закрываться автоматически, это будет видно по тексту title в этой строке, а не потеряется молча.

## Team Helper

`scripts/th-team-helper.user.js` — текущая версия: **1.30**.

Десять независимых помощников для ручного разбора тикетов. Каждый включается и выключается отдельно в блоке `CONFIG` в начале файла — если команде нужна только часть, лишнее гасится одной строкой:

```js
features: {
  filePreview:      true,   // превью вложений
  prevStatus:       true,   // предыдущий статус закрытых тикетов
  limitsFinder:     true,   // поиск лимитов по странице Confluence
  adminDirectory:   true,   // справочник админов в истории тикета
  messengerId:      true,   // автоподстановка своего Reddy ID
  autoDateRange:    true,   // автоподстановка дат в фильтр
  ticketCopy:       true,   // копирование данных тикета в буфер обмена
  commentTemplates: true,   // шаблонные комментарии для Change ticket
  fileButtons:      true,   // компактные кнопки вместо ссылок на файлы
  cellCopy:         true,   // копирование значения ячейки по клику
},
```

Отключать функции необязательно через код: круглая кнопка ⚙ в левом нижнем углу страницы открывает панель с тумблером на каждую из десяти функций (то же самое доступно через пункт меню Tampermonkey «Team Helper: Настройки»). Изменение применяется после обновления страницы, а сам выбор хранится через `GM_setValue` — переживает обновления скрипта и общий для всех трёх доменов. Подробности — в разделе «Панель настроек» ниже.

Работает на страницах `paymentsupport` и `ExtendedPaymentRequestList` на всех трёх доменах. Оформление подстраивается под тему админки.

С версии 1.3 в шапке стоит `@grant GM_xmlhttpRequest` и `@connect doc.office.lan` — это нужно поиску лимитов, чтобы обратиться к Confluence на другом домене. При первой установке Tampermonkey спросит разрешение на запрос к `doc.office.lan`, его надо подтвердить. Побочный эффект гранта: скрипт начинает работать в песочнице, где `window` уже не окно страницы, поэтому тему админки скрипт читает через `unsafeWindow`.

С версии 1.4 добавлены `@grant GM_getValue`, `@grant GM_setValue` и `@grant GM_registerMenuCommand` — хранилище для Reddy ID и пункт в меню Tampermonkey.

Справочник админов (версия 1.5) новых грантов не требует — он использует тот же `@connect doc.office.lan`, что уже подтверждён для поиска лимитов.

### Превью вложений

Наводишь курсор на ссылку в любой ячейке таблицы — рядом всплывает превью:

- **картинки** (`png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`) показываются целиком;
- **PDF и видео** (`mp4`, `webm`, `mov`, `avi`) — иконкой и именем файла;
- всё остальное игнорируется, попап не появляется.

В попапе две кнопки: **Fullscreen** (только для картинок) и **Open in new tab**. Полноэкранный просмотр листает **все картинки из той же ячейки** — стрелками на экране, клавишами `←`/`→`, со счётчиком `N / M`. Закрывается по `Esc`, крестику или клику по фону.

#### Поворот и масштаб в полноэкранном режиме

Под картинкой панель с кнопками:

| Кнопка | Действие |
|---|---|
| ↺ / ↻ | Поворот на 90° влево и вправо |
| − / + | Уменьшить и увеличить |
| `100%` | Сбросить поворот и масштаб (то же самое — двойной клик по картинке) |

Дополнительно:

- **колесо мыши** увеличивает и уменьшает картинку. Точка под курсором остаётся на месте, так что можно навести на нужный угол чека и приблизить именно его;
- **перетаскивание мышью** двигает увеличенную картинку. За собственные края её утащить нельзя — пустых полей по бокам не будет;
- при повороте картинка автоматически ужимается, чтобы целиком помещаться в экран: горизонтальный скриншот, повёрнутый на 90°, не обрежется по высоте;
- поворот и масштаб сбрасываются при переходе к следующей картинке и при закрытии просмотра.

Пределы масштаба задаются в `CONFIG`:

```js
filePreview: {
  zoom: {
    step: 1.15,   // во сколько раз меняется масштаб за одно деление колеса
    min: 1,       // 1 = картинка, вписанная в экран
    max: 8,       // предел увеличения
  },
  ...
}
```

Если картинка меньше экрана, она показывается в натуральную величину и при масштабе 100% остаётся по центру — двигать её в этом состоянии нечего.

#### Почему картинка остаётся чёткой при увеличении

Очевидный способ увеличить картинку — `transform: scale`. Он даёт плохой результат: браузер растрирует картинку один раз в её вёрстанном размере, и `scale` растягивает уже готовый растр, не обращаясь к оригиналу. Скриншот шириной 2400px, вписанный в экран как 912px, при увеличении показывает растянутые 912px вместо настоящих 2400px — детали теряются безвозвратно.

Поэтому скрипт меняет **вёрстанный размер** картинки (`width`/`height`), а не масштабирует её трансформацией. Браузер каждый раз растрирует её заново из полноразмерного оригинала, и вся детализация файла доходит до экрана.

Растр крупнее натурального разрешения смысла не имеет — новых деталей взять неоткуда, а памяти он требует много (8× от 2400×1600 — это 245 мегапикселей). Поэтому вёрстанный размер ограничен разрешением оригинала, а всё, что сверх него, догоняется через `scale`.

Под картинкой рядом со счётчиком показано **разрешение файла** — если изображение выглядит нечётким даже при небольшом увеличении, сразу видно, что оригинал просто мелкий, и дело не в просмотрщике.

Тип файла определяется по реальному пути: если ссылка ведёт на вьюер вида `/viewer?url=<путь>`, расширение берётся из параметра `url`, а открывается по-прежнему исходная ссылка.

Попап не исчезает, пока курсор на нём самом — иначе до кнопок нельзя было бы дойти. Если увести мышь на другую ссылку, пока картинка ещё грузится, старая загрузка отбрасывается и чужое изображение в попап не попадёт.

### Предыдущий статус

Наводишь на ячейку **External Status** со значением `Closed` или `Closed (M)` — скрипт запрашивает историю тикета (`POST /admin/backoffice/paymentsupporthistory`) и показывает, **какой статус был до закрытия** и когда. Ticket ID берётся из той же строки, колонки ищутся по названию в шапке таблицы.

История запрашивается один раз на тикет за сессию и кэшируется, так что повторные наведения ничего не грузят. Если увести мышь на другой тикет до ответа сервера, устаревший результат не отобразится.

Список статусов-триггеров задаётся в `CONFIG`:

```js
prevStatus: {
  triggers: ['closed', 'closed (m)'],
  ...
}
```

Чтобы расширить — дописать статусы в нижнем регистре, например `'credited'`, `'duplicated ticket'`. Учти, что каждый новый триггер добавляет запросы к серверу при обычном просмотре таблицы.

### Поиск лимитов в Confluence

Выделяешь мышью текст в ячейке колонки субагента — рядом всплывает окно с лимитами этого субагента, взятыми со страницы Confluence. Открывать саму страницу и искать по ней глазами не нужно. На разных листах сайта эта колонка называется по-разному (**Query Subagent** на одних, просто **Subagent** на других, например на `ExtendedPaymentRequestList`) — скрипт находит её по подстроке в названии, независимо от точной формулировки.

Как это работает:

- скрипт скачивает страницу Confluence и разбирает **все таблицы** на ней;
- совпадение ищется в первом столбце, по подстроке, без учёта регистра;
- над найденной строкой показывается ближайший заголовок страницы, то есть видно, из какого раздела лимит;
- если субагент встречается в нескольких таблицах, снизу появляется навигация `1 из 2` — переключение кнопками или стрелками влево-вправо;
- зачёркнутые в Confluence строки показываются серым с зачёркиванием, чтобы отменённый лимит не приняли за действующий;
- разметка Confluence очищается: остаётся читаемый текст с переносами строк, скрытые служебные дубли вырезаются.

Страница скачивается один раз за сессию и дальше берётся из памяти. Загрузка начинается заранее, как только курсор попадает на колонку субагента, поэтому окно обычно открывается мгновенно. Если запрос не прошёл, кэш сбрасывается и следующая попытка сходит за страницей заново.

Закрывается по `Esc`, клику мимо окна или прокрутке страницы.

Настройки:

```js
limitsFinder: {
  // ВАЖНО: проверьте, что это нужная вам страница
  pageUrl: 'https://doc.office.lan/spaces/MENA/pages/373073072/...',
  // В какой колонке работает выделение текста — подстрока, покрывает и
  // "Query Subagent", и просто "Subagent" на других листах сайта
  column: 'subagent',
  timeout: 15000,
  width: 340,
}
```

Адрес страницы взят из скрипта Team B. Если у вашей команды лимиты лежат в другом месте, замените `pageUrl`, менять что-то ещё не потребуется. Название колонки сравнивается по подстроке в нижнем регистре — специально короче полного названия, чтобы не зависеть от того, как именно колонка называется на конкретном листе.

Если окно показывает ошибку загрузки, причин обычно две: не подтверждено разрешение Tampermonkey на запрос к `doc.office.lan` или нет доступа к самой странице Confluence под текущей учётной записью. Проверяется открытием `pageUrl` в соседней вкладке.

### Справочник админов

В окне **«История тикета»** (Ticket history) есть колонка **Admin username** со значением вроде `pay_mena_429`. Наводишь курсор на такое значение — рядом всплывает тултип с именем и отделом сотрудника, который стоит за этим логином.

Не все значения в этой колонке — логины людей: там же встречаются системные и бот-аккаунты (`MT_Cash_Kittlite_Main`, `SOCRAT_bot` и подобные). Для них тултип честно показывает «Не найден в справочнике», а не ошибку.

Как это устроено:

- справочник хранится **отдельной страницей Confluence** (`doc.office.lan`) — того же домена, что уже используется поиском лимитов, поэтому новых разрешений Tampermonkey не требует;
- страница должна содержать ровно одну таблицу из трёх столбцов в фиксированном порядке: **логин | имя | отдел**. Столбцы читаются по позиции, а не по названию заголовка — писать шапку таблицы можно как угодно;
- страница скачивается один раз за сессию и разбирается в память; дальше каждое наведение — мгновенный поиск в уже загруженной карте, без обращений к серверу;
- таблица в окне истории тикета устроена иначе, чем в остальных таблицах админки: шапка — это `<tr class="table-head">`, а не `<thead>`. Скрипт ищет колонку по обоим вариантам разметки, поэтому справочник сработает и в такой таблице, и в обычной.

Настройки:

```js
adminDirectory: {
  // Страница «Расшифровка логинов L2 PS»
  pageUrl: 'https://doc.office.lan/spaces/MENA/pages/663814054/...',
  // Название колонки в окне «История тикета» (подстрока, в нижнем регистре)
  column: 'admin username',
  timeout: 15000,
  hideDelay: 150,
}
```

**Обновлять список — значит просто редактировать таблицу прямо на Confluence.** Ни версию скрипта поднимать, ни пересобирать ничего не нужно: изменения на странице подхватятся при следующей загрузке кабинета у того, кто наводит курсор.

Список сотрудников — персональные данные, поэтому он намеренно хранится не в этом (публичном) репозитории, а на внутренней странице, доступной только из корпоративной сети.

### Автоподстановка Reddy ID

Кнопка **Export to Reddy** открывает окно с полем **Reddy ID** — файл придёт в мессенджер Reddy тому, чей ID там указан. Раньше это поле приходилось заполнять своим ID вручную при каждом нажатии. Теперь скрипт делает это сам: как только окно появляется, поле заполняется автоматически, а отправляете вы сами — скрипт ничего не подтверждает и не отправляет за вас.

ID берётся не вручную, а прямо со страницы админки: он лежит в её служебной разметке (атрибут `curr_medium` на компоненте `leftpanel`), и скрипт находит его там при первой же загрузке страницы. Найденное значение сохраняется в хранилище Tampermonkey — общем для всех трёх доменов и переживающем обновления скрипта — и дальше используется без повторных запросов. Практически это означает, что для каждого в команде подставится его собственный ID, и настраивать ничего не нужно.

Если в вашем профиле Reddy не заполнен или нужно временно подставлять чужой ID (например, отправить файл коллеге), в меню Tampermonkey есть пункт **Team Helper: мой Reddy ID** — там можно посмотреть текущее значение, задать своё или очистить поле, чтобы скрипт заново определил ID со страницы.

Важное правило: скрипт заполняет поле, только если оно **пустое**. Если вы сами вписали туда чужой ID, скрипт это не тронет.

Настройки:

```js
messengerId: {
  storageKey: 'reddyId',        // ключ в хранилище Tampermonkey
  sourceAttr: 'curr_medium',    // атрибут в разметке страницы, откуда берётся ID
  fieldPlaceholder: 'Reddy ID', // по этому плейсхолдеру скрипт находит поле в окне
}
```

Поле ищется по плейсхолдеру, а не по кнопке, которая открывает окно, — значит, подстановка сработает независимо от того, с какой кнопки или таблицы вызвано окно, если плейсхолдер поля такой же.

### Автоподстановка дат

После нажатия **Apply** в модалке фильтров скрипт сам заполняет поле диапазона дат значением **примерно год назад → сегодня**. Дата «от» — не фиксированная точка, а случайный день в пределах месяца после «год назад» (ближе к текущей дате), новый на каждое нажатие Apply:

```
14.08.2025 00:00 ~ 13.08.2026 23:59
```

Правило задаётся в `CONFIG`:

```js
autoDateRange: {
  yearsBack: 1,          // на сколько лет назад отсчитывать точку отсчёта
  shiftDays: [1, 30],    // случайный сдвиг даты «от» вперёд, в днях
  startTime: [0, 0],     // время начала диапазона
  endTime: [23, 59],     // конец диапазона — всегда сегодня
  ...
}
```

Минимальный сдвиг в 1 день гарантирует, что диапазон не выйдет за годовое окно (как и раньше с `daysOffset`), а заодно дата «от» никогда не совпадает ровно с точкой «год назад». Время «от» всегда 00:00 — случайны только дни.

Значение ставится нативным сеттером с событиями `input` и `change` — иначе Vue не заметит изменение поля. Если после Apply поле ещё не отрисовано, скрипт повторяет попытку каждые 100 мс в течение 3 секунд и затем сдаётся.

### Копирование данных тикета

В форме **«Change ticket…»** в правом верхнем углу окна появляется кнопка **«Данные тикета»** (оверлеем поверх карточки модалки, `position: absolute` — до версии 1.26 она стояла рядом с полем **Comment (internal)**, ниже в форме). По клику открывается окно, которое:

- собирает десять полей текущего тикета — Subagent, User ID, Amount by receipt, Payment creation date, Agent wallet, User's wallet, Recipient department, Transaction ID, Unique transfer number, Agent;
- даёт выбрать один из трёх готовых вариантов комментария в первой строке (без комментария / «Лимит + возврат из Request for a refund» с двумя подпереключателями / «Подозрительный скриншот»);
- показывает живое превью итогового текста;
- предупреждает, если какое-то из полей не заполнено (в тексте вместо него — «—»);
- копирует готовый текст в буфер обмена одной кнопкой, с подтверждением «Скопировано».

Как это устроено:

- сама кнопка вставляется в `.modal_content` (карточку диалога) — общего родителя всех полей формы, а не привязана к конкретному полю. Кнопка ждёт появления шапки тикета (`.success-txt`), а по её высоте вычисляет отступ сверху так, чтобы вставать точно по центру шапки, а не по подобранному на глаз отступу — число строк в шапке (User ID / Transaction ID / ... / Country) отличается от тикета к тикету;
- перед вставкой скрипт дополнительно проверяет наличие поля `Comment (internal)` именно внутри этой карточки (`CONFIG.ticketCopy.modalMarkerField`) — общая вёрстка модалок (`.modal_wrap`/`.modal_content`) и класс `.success-txt` (просто зелёный текст) встречаются и в других диалогах сайта, например в «Saved filters», и без этой проверки кнопка вылезала бы и там;
- поля для сбора данных ищутся по заголовку (`.input-group` + `.title`), а не по порядку в форме — устойчиво к перестановке полей на странице;
- Subagent, Agent и Recipient department берутся из редактируемых полей формы (`multiselect`), а не из шапки тикета — если оператор их меняет прямо в форме, скопируется актуальное значение;
- User ID берётся из шапки тикета (`<strong>User ID:</strong> …`), отдельного редактируемого поля для него нет;
- Transaction ID сначала ищется как редактируемое поле формы, и только если оно пустое — берётся из шапки тикета (там обычно лежит транзакция из исходного запроса);
- буфер обмена — обычный `navigator.clipboard`, с запасным вариантом через скрытое поле ввода, если он недоступен. Новых грантов Tampermonkey не потребовалось.

Настройки:

```js
ticketCopy: {
  modalMarkerField: 'Comment (internal)', // по этому полю отличаем форму тикета от других диалогов сайта
  fields: {
    subagent: 'Subagent',
    userId: 'User ID',
    amount: 'Amount by receipt',
    date: 'Payment creation date',
    agentWallet: 'Agent wallet',
    userWallet: "User's wallet",
    recipientDepartment: 'Recipient department',
    transactionId: 'Transaction ID',
    uniqueTransferNumber: 'Unique transfer number',
    agent: 'Agent',
  },
  emptyPlaceholder: '—', // чем заменяется пустое значение поля
  comments: [ /* варианты комментария, см. текст скрипта */ ],
  tableRowButtonColumn: 'Ticket history', // колонка обычной таблицы для кнопки — есть на всех листах, в отличие от Actions
  // Короткий набор полей для кнопки в таблице — сознательно меньше, чем
  // fields выше: для быстрого копирования без модалки нужны не все десять
  tableFields: {
    subagent: 'Subagent',
    userId: 'User ID',
    ticketId: 'Ticket ID',
    recipientDepartment: 'Department',
    country: 'Country',
  },
}
```

Формат самих строк итогового текста (`User ID:`, `Amount:` и т.д.) в `CONFIG` не вынесен — это фиксированный формат, который команда вставляет в чат. Поменять формулировки комментариев можно прямо в `CONFIG.ticketCopy.comments`.

Та же самая функция доступна и без открытия Edit: в колонке **Ticket history** обычной таблицы (та же ячейка, что и ссылка «Show» — эта колонка есть на всех листах, в отличие от Actions, которой нет, например, на `ExtendedPaymentRequestList`) у каждого тикета есть компактная кнопка-иконка. По клику копируются сразу в буфер — без модалки и без выбора шаблона комментария — **пять** полей: Subagent (первой строкой, без `// комментарий`), User ID, Ticket ID, Department, Country. Это сознательно урезанный набор по сравнению с модалкой (там все десять) — для быстрой вставки в чат обычно нужны только эти пять. Кнопка на секунду показывает галочку вместо иконки как подтверждение.

Кнопка идёт в общем потоке сразу после ссылки «Show»: обе обёрнуты в `<span class="th-tc-history-cell">` с `display: inline-flex` и `white-space: nowrap`, поэтому они всегда остаются на одной строке, даже в узкой колонке, и не переносятся друг под друга. До версии 1.25 кнопка была закреплена оверлеем (`position: absolute` внутри `position: relative` на ячейке) — это решало проблему переноса, но на обычной прокрутке страницы колесом мыши иногда на долю кадра «отлипала» от своей строки и съезжала наверх (баг рендеринга абсолютно спозиционированных элементов с `transform` внутри ячейки таблицы). Вёрстка через flex вместо `position: absolute` убирает саму возможность такого глюка.

Заголовки колонок обычной таблицы не совпадают дословно с названиями полей формы Edit (например, `Department` вместо `Recipient department`) — поэтому у них отдельная карта `CONFIG.ticketCopy.tableFields`, а не общая с `fields`, и состав полей в ней тоже другой (пять вместо десяти).

### Шаблонные комментарии для Change ticket

Ещё одна кнопка в форме **«Change ticket…»** — **«Добавить шаблонный комментарий»**, встроена в поток сразу после заголовка поля **Comment (internal)**. Появляется только для конкретного набора статусов тикета, для остальных статусов не показывается вовсе. Функция портирована из соседнего скрипта команды («Edit Helper Team B»), который был написан для совместной работы с Team Helper, но сам эту кнопку не добавлял — оставлял её нам.

По клику открывается модалка, форма которой зависит от статуса:

- **209 / 55** — список из пяти вариантов, один из них («Ошибка агента (найдено зачисление)») просит номер транзакции и подставляет его в текст;
- **207** — выбор «ниже лимита» / «выше лимита»;
- **210 / 90** — одно поле «Original Ticket ID»;
- **216 / 98** — переключатель «есть/нет одобренная транзакция» + динамический список Ticket ID (добавить/удалить) — эскалация в антифрод;
- **243 / 72** — одно поле «Номер транзакции»;
- **240 / 97** — список из пяти вариантов ожидания ответа (agent/senior/NR/TA/MN).

Выбранный текст вставляется в `Comment (internal)` с префиксом `// ` (настраивается), новой строкой, если в поле уже что-то есть — с диспатчем `input`/`change`, как и остальные функции скрипта, пишущие в поля формы.

Как это устроено:

- в отличие от исходного скрипта-донора (там статус и комментарий искались по всему `document`), здесь оба поля — **Status** и **Comment (internal)** — ищутся строго внутри карточки открытого тикета (`.modal_content`), без отката к document. Так кнопка не путает статус тикета со сторонним фильтром Status на странице и не реагирует на другие открытые диалоги;
- статус определяется по числу в начале названия (`"209 - Approved with correction (M)"` → `209`) — под одну и ту же группу шаблонов может попадать несколько ID сразу (например, `209` и `55` дают одинаковый набор);
- кнопка на статус реагирует "живьём": если оператор меняет Status, пока форма открыта, кнопка появляется/исчезает по тому же `MutationObserver`, что подхватывает и остальные динамические изменения формы; клик всегда читает статус заново на момент нажатия, а не на момент появления кнопки;
- независимый тумблер `commentTemplates` в панели настроек — можно выключить отдельно от кнопки «Данные тикета».

Настройки:

```js
commentTemplates: {
  statusField: 'Status',
  commentField: 'Comment (internal)',
  prefix: '// ',
  groups: [
    { ids: ['209', '55'], kind: 'options', options: [ /* см. текст скрипта */ ] },
    { ids: ['207'], kind: 'options', options: [ /* ... */ ] },
    { ids: ['210', '90'], kind: 'input', label: 'Original Ticket ID', placeholder: '...', template: (val) => `...` },
    { ids: ['216', '98'], kind: 'antifraud', radios: [ /* ... */ ], template: (ids, txn, hasApproved) => `...` },
    { ids: ['243', '72'], kind: 'input', label: 'Номер транзакции', placeholder: '...', template: (val) => `...` },
    { ids: ['240', '97'], kind: 'options', options: [ /* ... */ ] },
  ],
}
```

Чтобы добавить новый статус или изменить тексты — правится только `CONFIG.commentTemplates.groups`, без изменений в остальном коде.

### Кнопки вместо ссылок на файлы

В колонках **User files**, **Agent's files** и **Support team's files** длинные ссылки вида `WebUserDocuments/889142155/Consultant/a32456d4b2e913dde2fd6630ac2240c1….jpg` заменяются компактными кнопками — `1. Скрин`, `2. PDF`, `3. Видео`. Строки таблицы перестают растягиваться, а по наведению на кнопку по-прежнему работает превью вложений.

Кнопки окрашены по типу файла: изображения — бирюзовым (как и раньше), **PDF — оранжевым**, **видео — фиолетовым**, а всё остальное (аудио, документы, таблицы, архивы и любое незнакомое расширение) — **красным**, чтобы такие вложения не терялись среди остальных.

Как это устроено:

- нужные колонки ищутся **по названию заголовка**, а не по номеру — если колонки в таблице переставят местами, ничего не сломается. Регистр, лишние пробелы, неразрывные пробелы и разные апострофы (`Agent's` / `Agent’s`) при сравнении не важны;
- в окне **«История тикета»** та же по смыслу колонка, что в основной таблице называется **Support team's files**, называется **Internal files** — оба варианта в списке колонок, поэтому кнопки появляются в обоих окнах;
- тип файла определяется по реальному пути из параметра `?url=` в ссылке, а не по её тексту — поэтому подпись и цвет остаются правильными даже после замены текста;
- **нумерация идёт по порядку кнопок в ячейке** (слева направо), поэтому номера совпадают и с тем, что видно на экране, и с порядком листания в полноэкранном просмотре;
- сам адрес ссылки не меняется — в `title` кнопки остаётся настоящее имя файла, а клик открывает файл в новой вкладке;
- ссылки `javascript:` пропускаются, повторная обработка одной и той же ссылки исключена флагом на элементе — новые строки после пагинации подхватываются автоматически.

Настройки:

```js
fileButtons: {
  // В каких колонках ссылки заменяются кнопками
  columns: ['user files', "agent's files", "support team's files", 'internal files'],
  // Подпись и цветовая категория (kind) кнопки по расширению файла.
  // kind: 'image' | 'pdf' | 'video' | 'other' — своим цветом выделены
  // только pdf и video, остальное (в т.ч. незнакомые расширения) — 'other'
  types: {
    'Скрин': { exts: ['jpg', 'jpeg', 'png', 'webp', ...], kind: 'image' },
    'PDF':   { exts: ['pdf'], kind: 'pdf' },
    'Видео': { exts: ['mp4', 'webm', 'mov', ...], kind: 'video' },
    ...
  },
  fallbackLabel: 'Файл',  // для неизвестных расширений
  fallbackKind: 'other',
}
```

Чтобы добавить новый тип файла, переименовать подпись или сменить цветовую категорию, достаточно поправить `CONFIG.fileButtons.types` — расширения перечисляются в нижнем регистре.

### Копирование значения ячейки

Наводишь курсор на любую ячейку таблицы с обычным текстом — курсор меняется на «указательный палец» (как над обычной ссылкой), сигнализируя, что по ячейке можно кликнуть. Клик в любом месте ячейки копирует в буфер ровно то, что в ней написано, без выбора и форматирования — для случаев, когда нужно быстро скопировать одно значение, а не весь набор полей тикета. Спустя примерно 300мс после клика ячейка на мгновение подсвечивается зелёным — подтверждение, что копирование прошло.

Как это устроено:

- интерактивными становятся только ячейки с обычным текстом — ячейки со своими ссылками или кнопками (**Ticket history** со ссылкой «Show», колонки с кнопками файлов) и пустые ячейки пропускаются, там копировать нечего или непонятно что;
- никакой кнопки в разметке нет — `cursor: pointer` и подсветка при копировании навешаны прямо на ячейку через класс `th-cc-cell`, обработчик клика — тоже на ней;
- копирование срабатывает не мгновенно на клик, а спустя ~300мс — за это время браузер успевает понять, не второй ли это клик двойного клика. Если пришёл второй клик (обычный способ выделить слово в ячейке — например, чтобы найти по нему лимит через «Поиск лимитов в Confluence», см. выше), отложенное копирование отменяется и не мешает выделению;
- то же самое для протягивания мышью (drag-select) — если к моменту срабатывания в ячейке есть активное текстовое выделение, копирование не происходит, чтобы не переписать буфер поверх того, что человек выделил сам;
- отдельный тумблер `cellCopy` в панели настроек — можно выключить независимо от общей кнопки копирования тикета («Копирование данных тикета» выше), если клики по ячейкам мешают;
- новые строки таблицы (после пагинации, фильтра) подхватываются тем же `MutationObserver`, что и у остальных функций с динамическими таблицами.

### Панель настроек

Круглая кнопка ⚙ в левом нижнем углу страницы открывает панель со списком всех десяти функций и тумблером напротив каждой. Тот же список открывается через меню Tampermonkey → «Team Helper: Настройки» — на случай, если кнопка на странице потеряется среди вёрстки сайта.

Как это устроено:

- `CONFIG.features` в шапке скрипта задаёт значение **по умолчанию** — если панелью ещё ни разу не пользовались, тумблеры показывают именно его;
- переключение тумблера сразу сохраняется через `GM_setValue` (общее хранилище для всех трёх доменов, переживает обновления скрипта) и **не требует нажатия «Сохранить»**;
- изменения не применяются мгновенно — уже загруженные функции успели навесить обработчики и наблюдатели за DOM, аккуратно откатить это «на лету» нельзя. После первого переключения в панели появляется подсказка «Изменения вступят в силу после обновления страницы» с кнопкой **Обновить**;
- панель закрывается по клику на затемнение, по `Escape` или повторным кликом на кнопку ⚙; при каждом открытии тумблеры и подсказка сбрасываются к актуальному сохранённому состоянию.

### Диагностика

По умолчанию скрипт молчит. Чтобы посмотреть, что он делает, поставить в `CONFIG`:

```js
debug: true,
```

Тогда в консоли (F12 → Console) появятся строки вида `[TeamHelper] Диапазон дат подставлен: ...`, `[TeamHelper] Не удалось получить историю тикета ...`.

## Dark Theme Recolor

`scripts/th-dark-theme.user.js` — текущая версия: **1.0**.

### Что делает

Перекрашивает встроенную тёмную тему сайта в более тёмную и контрастную: базовые поверхности, текст, тултипы/дропдауны — через CSS-переменные темы; таблицы (шапка, зебра, рамки, строки без тёмного варианта в CSS сайта), кнопки `.btn-success`, теги фильтров, пагинацию и кастомный скроллбар — через `!important`-переопределения, потому что эти цвета захардкожены в CSS сайта и переменными не задеваются.

Работает только при активной тёмной теме сайта (`window._THEME === 'dark'`) — при светлой теме ничего не делает. В отличие от Team Helper, `@match` — весь сайт на всех трёх доменах, а не только страницы тикетов (см. [«Как устроена система»](#как-устроена-система)).

Гранты не нужны — скрипт работает без песочницы (`@grant none`), поэтому тема читается напрямую через `window._THEME`, без `unsafeWindow`.

## Обновление скриптов

1. Внести изменения в нужный файл в `scripts/`.
2. Увеличить `@version` в шапке скрипта — без этого Tampermonkey не увидит обновление.
3. Запушить изменения в `main`.

Tampermonkey периодически (или по кнопке «Check for updates» в панели) сверяет `@version` по ссылке из `@updateURL` и подтягивает новый код с `@downloadURL`. Пока изменения не в `main` — установленные у пользователей копии их не увидят.
